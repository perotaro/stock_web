# Second Opinion

## 概要

このスキルは、以前の回答や判断を独立した立場から再評価するために使う。
同意することではなく検証することを優先し、事実・推論・推測を明確に分けて扱う。

## 基本ルール

- もっともらしいという理由だけで以前の回答を擁護しない。
- 前のエージェントと結論を合わせることを目的にしない。
- 可能なら親エージェントがそのまま答えず、独立したサブエージェントに検証を担当させる。
- コード、テスト、ログ、ドキュメント、仕様、一次資料を優先して確認する。
- 証拠が足りない場合は、その不足を明示する。
- 確認済みの事実、妥当な推論、未解決の不確実性を分けて書く。
- 暗黙の前提、抜けている制約、境界条件を積極的に疑う。
- 広いが弱い主張より、狭くても根拠のある主張を優先する。
- ユーザーが別言語を求めない限り、ユーザーの言語に合わせる。

## 確認対象として集めるもの

以前の回答を検証するときは、次のような最小限の生データを集める。

- 検証対象となる以前の回答そのもの、または主張の原文
- コード、テスト、ログ、要件、ドキュメント、差分などの根拠資料
- 結論に影響するユーザー制約
- 日付やバージョンが効く話題なら、その時点情報

複数の主張がまとめて含まれている場合は、主張ごとに分解して確認する。

## サブエージェント実行方針

このスキルが呼ばれたら、可能な限り次の方針で独立したサブエージェントを起動して評価させる。

1. `spawn_agent` を使って別エージェントを起動する。
2. `fork_context` は原則 `false` にする。
3. 親の結論や診断は渡さず、検証対象の主張、前の回答本文、コード、ログ、差分、仕様などの一次情報だけを渡す。
4. モデルは既定では `gpt-5.4` を優先し、重すぎる場合だけ `gpt-5.4-mini` に下げる。
5. 推論量は既定では `high` を使い、重要判断や複雑な論点だけ `xhigh` を使う。
6. サブエージェントの返答を受けた後、親エージェントは要約や整形だけを行い、未検証の断定を足さない。

サブエージェントが使えない環境では、このスキルのルールに従って親エージェントが代替実行する。ただしその場合は、独立性が弱くなることを明示する。

## 評価フロー

1. 対象となる主張を中立的に言い換える。
2. 何が直接検証できるかを切り分ける。
3. まず一次的な根拠を確認する。
4. 主要な主張ごとに次のいずれかで判定する。
   - 根拠あり
   - もっともらしいが未検証
   - 根拠が弱い、または不足している
   - 誤っている
5. 重要な前提漏れや別解釈があれば書く。
6. 費用対効果の高い次の確認手順を提案する。

## 出力形式

ユーザーから別指定がなければ、次の順で答える。

1. 結論
2. 正しそうな点
3. 弱い点、根拠不足の点、誤っている点
4. まだ検証が必要な点
5. 次にやるべきこと

前置きは短くし、所見を先に書く。

## よくあるケース

- コードに関する質問では、リポジトリ、差分、テスト、実行時挙動を見てから結論を支持する。
- デバッグ方針では、再現手順の欠落、環境依存の仮定、提案された原因が症状全体を説明できているかを見る。
- 設計提案では、トレードオフ、見落とした制約、移行コスト、可逆性、故障時の影響を見る。
- 見積もりや優先度判断では、事実と判断を分離し、結論が変わる前提条件を明示する。
- 事実主張では、根拠元を確認するか、未検証であることを明示する。

## 依頼例

- "`$second-opinion` を使って、前の説明が本当にコードで裏付けられているか確認して"
- "`$second-opinion` を使って、このデバッグ結論の弱い点と未証明の点を洗い出して"
- "`$second-opinion` を使って、この設計案を客観的に見てトレードオフの抜けを指摘して"
- "`$second-opinion` を使って、前の回答をリンク先ドキュメントと照合して"
- "`$second-opinion` を使って、独立サブエージェントで前の回答を再検証して"

## 避けること

- 何を確認したか示さずに「問題なさそう」とだけ言わない。
- 断定的に見せるために不確実性を隠さない。
- 事実確認や挙動確認の話で、単なる好みの議論にすり替えない。
- 複数の独立した確認手段があるのに、1つの根拠だけに依存しない。
- 以前の回答を言い換えただけのものを検証結果として出さない。
