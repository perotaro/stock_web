# Guppy フロントエンドビジュアル設計

## 1. 文書目的
本書は、Guppy Webシステムにおけるフロントエンドのビジュアル設計を定義する。  
初期段階では公開トップページ `/` を対象とし、表示情報、レイアウト、見た目のトーン、コンポーネントの使い方、実装時の判断基準を明確化することを目的とする。

本書はフロントエンド基本設計を補完する文書であり、見た目を過度に作り込むことではなく、情報の優先順位が明確で、実装しやすく、保守しやすい UI を定義することを重視する。

## 3. スコープ

### 3.1 対象
- 公開トップページ `/` の視覚設計
- API 返却項目と表示内容の対応
- トップページのセクション構成
- 共通デザイン指針の公開トップへの適用方法
- モバイルおよびデスクトップのレイアウト方針

### 3.2 対象外
- `/login` `/app` `/app/systems/:system_code` `/app/watchlist` の詳細ビジュアル設計
- アニメーションの詳細設計
- Figma などのデザインツール上の作業手順
- 実装時の CSS クラス名やコンポーネント props の詳細定義

## 4. 前提
- 対象画面は公開トップページ `/` とする。
- 公開トップで利用する API は `GET /api/v1/public/summary` とする。
- 表示してよい情報は匿名集計値に限定する。
- 公開トップでは GitHub への外部リンクを置かない。
- 公開トップでは個別銘柄、戦略詳細、当日シグナル生データを表示しない。
- トップページの第一目的は、サービス概要と公開可能な運用状況を短時間で理解できることとする。
- 第二目的は、認証後画面へのログイン導線を自然に提供することとする。

## 5. API 項目と表示対応

### 5.1 取得項目
公開トップページでは、以下の項目のみを表示対象とする。

| API 項目 | 画面表示名 | 表示ルール |
|---|---|---|
| `operating_days` | 当月稼働日数 | `xx日` 形式で表示する |
| `batch_runs_total` | 総実行回数（累計） | 3桁区切りの整数で表示する |
| `success_rate` | 当月成功率 | `%` 表記で表示する |
| `avg_duration_sec` | 当月平均処理時間 | `xx.x 秒` を基本とする |
| `updated_at` | 最終更新日時 | `JST` 表示に統一する |

### 5.2 表示禁止項目
以下は公開トップページで表示しない。

- システム数
- 監視対象件数
- 個別銘柄情報
- 戦略ロジック
- 当日シグナルの生データ
- 運用者向け内部情報

## 6. 共通デザイン指針の参照

- 色、タイポグラフィ、余白、ボタン、カード、ヘッダ、レスポンシブなどの全画面共通ルールは [DESIGN.md](/workspace/apps/frontend/DESIGN.md) を正本とする。
- 本書では公開トップページ `/` 固有の情報構造、レイアウト、文言、状態表示、導線配置のみを定義する。
- 本書の記述が共通指針と競合する場合、公開トップに限定した例外として明示されている内容だけを優先し、それ以外は `DESIGN.md` に従う。

## 7. 情報構造

### 7.1 セクション構成
公開トップページ `/` は以下の 4 セクションで構成する。

1. ヘッダ
2. ヒーロー
3. 匿名集計サマリ
4. 公開範囲の説明

### 7.2 セクションごとの役割
| セクション | 主な役割 | 主な内容 |
|---|---|---|
| ヘッダ | ブランド識別子と最小限の導線を示す | 横長ロゴ画像、ログインボタン |
| ヒーロー | サービス概要と更新されている印象を伝える | 見出し、説明文、最終更新日時 |
| 匿名集計サマリ | 公開可能な実績サマリを見せる | 4つの匿名集計カード |
| 公開範囲の説明 | 何を公開しているかを明確にする | 匿名集計のみであることの説明 |

## 8. レイアウト設計

### 8.1 デスクトップレイアウト
- ヘッダは独立した暗色帯とし、左に横長ロゴ画像、右にログインボタンを置く。
- ロゴ画像は暗色背景上で十分なコントラストを持つ透過画像を使う。
- ヘッダとヒーローは同系色で連続して見えてもよいが、物理的には別ブロックとし、重なりを発生させない。
- ヒーローは 2 列に分けず、テキスト主体の 1 カラムとする。
- ヒーローはヘッダ直下に配置するが、ヘッダの高さぶんを侵食せず、明確な開始位置を持たせる。
- `最終更新日時` はヒーロー直下の補助情報として配置する。
- 匿名集計カードは白い面の上に `2 x 2` の 4 枚構成で置く。
- 公開範囲の説明は、カードではなく淡い面と区切り線で分ける。

### 8.2 モバイルレイアウト
- すべて 1 カラムで積み上げる。
- ヘッダの導線は右上の `ログイン` ボタンのみとする。
- 匿名集計カードは 4 枚を縦積みにする。
- テキスト量はデスクトップよりもさらに短く保つ。
- 冒頭の暗色面は維持するが、高さを伸ばしすぎずファーストビューで主要情報が見えるようにする。
- モバイルでもログイン導線はヘッダ右上の 1 箇所に固定し、ヒーロー内にボタンを置かない。

## 9. 公開トップでの適用ルール

### 9.1 面構成
- 公開トップは `暗色ヘッダ -> 暗色ヒーロー -> 明色の匿名集計サマリ -> 中間面の公開範囲説明` の順で構成する。
- 全画面共通の配色、余白、角丸、境界線、タイポグラフィは [DESIGN.md](/workspace/apps/frontend/DESIGN.md) に従う。

### 9.2 公開トップ固有のヘッダ適用
- ヘッダ左は横長ロゴ画像、右は `ログイン` ボタンとする。
- このログインボタンは公開トップページ専用とし、サイト全体の共通導線ルールにはしない。
- ヘッダはヒーローに重ねず、独立した行として配置する。

### 9.3 公開トップ固有の情報面適用
- 匿名集計サマリだけをカードグリッドとして扱う。
- 公開範囲の説明はカード化せず、本文と区切り線または中間面で見せる。
- ヒーロー内やページ下部に重複したログインボタンは置かない。

## 10. コンポーネント設計

### 10.1 Header
- 左に横長ロゴ画像
- 右に `ログイン` ボタン
- ヘッダはヒーローに重ねず、独立した行として配置する
- このログインボタンは公開トップページ専用とし、サイト全体の共通導線ルールには昇格させない

### 10.2 Hero
- 大きな見出し
- 2 行以内の説明文
- `updated_at` を使った最終更新日時表示
- ログイン導線は持たず、操作要素はヘッダ右上ボタンに委ねる

### 10.3 MetricCard
- 匿名集計サマリ専用
- 要素は `見出し / 値 / 補助説明` の 3 段に限定する
- 補助説明が不要な場合は 2 段でもよい

### 10.4 DisclosureSection
- 公開範囲の説明用テキストブロック
- カード化せず、本文と区切り線で構成する

## 11. 表示文言案

### 11.1 見出し
`日次更新のシグナルを、公開サマリと認証後画面で確認できる。`

### 11.2 説明文
`公開領域では匿名集計と更新状況のみを表示します。詳細な判定結果や対象一覧はログイン後に確認できます。`

### 11.3 公開範囲の説明
`表示内容は匿名集計に限定しており、個別銘柄、戦略詳細、当日シグナル生データは公開しません。`

### 11.4 ログイン導線
- ヘッダー右上ボタン: `ログイン`

## 12. 状態表示設計

### 12.1 ローディング
- ヒーロー直下または匿名集計セクション上部に簡潔なローディング表示を置く。
- スケルトンを使う場合は、4 枚の匿名集計カード部分だけに限定する。

### 12.2 エラー
- 公開トップの上部または匿名集計セクション直前にエラーメッセージを表示する。
- 文言は簡潔にし、`再試行` ボタンを併設する。
- API の内部情報や詳細エラー文字列は表示しない。

### 12.3 データ欠損
- 項目単位の欠損は `--` 表示を基本とする。
- ページ全体を空白状態にせず、最低限の説明文と導線を残す。

## 13. 実装時の注意
- `/` では API 項目にないメトリクスを見た目の都合で追加しない。
- ヒーローと公開範囲説明はカード化しない。
- 数字の単位を UI 側で必ず明示する。
- `updated_at` は `JST` 表示に統一する。
- モバイル表示でカードの横並びを維持しようとせず、素直に 1 カラムへ落とす。
- ヘッダを固定表示する場合でも、ヒーローと重なる見た目を作らず、ヘッダ高さぶんの余白を確保する。
- ログイン導線はヘッダー右上のボタンだけに集約し、ヒーローやページ下部に重複ボタンを置かない。
- ログインボタンの配置は公開トップページに限定し、他画面では画面責務に応じて別導線を設計する。

## 14. 今後拡張時の扱い
- 将来、公開トップ API に返却項目が追加された場合でも、セクション構成を崩さず匿名集計セクションの中で吸収することを基本とする。
- 追加項目が数値以外の場合は、安易にカード化せず、本文セクションまたは別導線の追加で解決できるかを先に検討する。
- ログイン後画面のビジュアル設計は、本書とは別節または別文書で追加する。
