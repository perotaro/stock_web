# Guppy フロントエンドビジュアル設計

## 1. 文書目的
本書は、Guppy Webシステムにおける主要ユーザー向け画面のビジュアル設計を定義する。  
対象は公開トップページ `/`、公開導線 `/login` `/logout`、認証後画面 `/app` `/app/systems/:system_code` `/app/watchlist` とし、各画面の情報優先順位、レイアウト、状態表示、モバイル方針を明確化することを目的とする。

本書は [フロントエンド基本設計](/workspace/docs/design/frontend_basic_design.md) を補完する文書であり、見た目の装飾よりも、情報が整理され、実装しやすく、保守しやすい UI を定義することを重視する。

## 3. スコープ

### 3.1 対象
- 公開トップ `/` の視覚設計
- 公開導線 `/login` `/logout` の視覚設計
- 認証後共通フレームの視覚設計
- `/app` `/app/systems/:system_code` `/app/watchlist` の視覚設計
- API 返却項目と画面表示の対応
- 画面ごとの情報構造、状態表示、モバイル方針

### 3.2 対象外
- `/auth/callback` `/auth/logout/callback` の詳細ビジュアル設計
- アニメーションの詳細設計
- 実装時の CSS クラス名、props、DOM 構造の詳細
- Figma 等のデザインツール上の作業手順

## 4. 前提
- 共通の色、タイポグラフィ、余白、角丸、ボタン、カードの基準は [DESIGN.md](/workspace/apps/frontend/DESIGN.md) を正本とする。
- 公開導線と認証後導線は同じブランドトーンを維持するが、情報密度と面構成は明確に切り替える。
- 公開画面では匿名集計のみを見せ、個別銘柄、戦略詳細、当日シグナル生データは表示しない。
- 認証後画面では、更新状況の把握と詳細画面への遷移を優先し、装飾的な要素は増やさない。
- すべての日時表示は JST で統一する。

## 5. 共通ビジュアルルール

### 5.1 面構成
- 暗色面は構造と導線を担う。
- 明色面は情報と操作を担う。
- 補助説明はカードを増やしすぎず、中間面または余白で分離する。

### 5.2 共通コンポーネント単位
- `GlobalHeader`
  - 全ページ共通で使う暗色ヘッダ
  - 左側は常にブランドロゴ、右側はページ群ごとのアクション領域とする
- `PageHeader`
  - ページタイトル、短い説明、補助メタ情報をまとめる
- `AppSectionNav`
  - 認証後ページで `Summary` `Watchlist` などの同階層ページを切り替える
  - `PageHeader` 直下に置き、現在地はリンクにしない
- `SectionPanel`
  - 各セクションの主要な情報面を受ける
- `StatusPill`
  - 状態を色と文字ラベルで同時に示す
- `InlineError`
  - セクション内エラーを簡潔に示す
- `EmptyState`
  - 正常系空状態を説明文付きで示す

### 5.3 状態表示の原則
- ローディング時もヘッダと主要導線は維持し、ページ全体を空白にしない。
- エラーは API の詳細文字列を露出せず、対象セクション内の問題として示す。
- 空状態は「データがない」ことと「失敗した」ことを分けて表現する。
- 状態の違いを色だけで判別させず、必ず文言も併記する。

### 5.4 レスポンシブ原則
- モバイルでは 1 カラムを基本とする。
- タブレット幅で表が窮屈になる場合は、横スクロールよりカード化を優先する。
- ファーストビューではページタイトルと最初の主要セクションが見える状態を維持する。

## 6. 全ページ共通ヘッダ

### 6.1 役割
- 全ページでトップページと同じヘッダ骨格を使う。
- 左側は常にロゴ画像、右側は画面群ごとの主要導線に限定する。
- ヘッダ自体にページ固有の説明を持たせず、文脈はページ本文側で補う。

### 6.2 ヘッダ構成
- 左側は横長ロゴ画像を固定で置く。
- 右側はページ群ごとに切り替える。
  - `/`: `ログイン`
  - `/login` `/logout`: `公開トップへ戻る`
  - `/app*`: `Logout`
- システム詳細画面の現在地は、グローバルヘッダではなくページヘッダ内の `system_code` で補う。
- ヘッダは本文に重ねず、独立した帯として扱う。

### 6.3 認証後ページ共通ナビ
- `/app` `/app/watchlist` `/app/systems/:system_code` では、グローバルヘッダとは別に `PageHeader` 直下へ `AppSectionNav` を置く。
- `AppSectionNav` の候補は `Summary` `Watchlist` とし、現在地は強調表示だけを行い、リンクやボタンにしない。
- `/app/systems/:system_code` では、`AppSectionNav` はアプリ内の主要ページ切り替えとして扱い、現在見ているシステムの文脈は `PageHeader` 内のタイトルと補助情報で示す。
- グローバルヘッダはアカウント操作、`AppSectionNav` はアプリ内移動と役割を分ける。

### 6.4 コンテンツ構成
- 各ページ先頭に `PageHeader` を置く。
- 主要データ面は `SectionPanel` 単位で分ける。
- ページごとの固有ロジックはページ本体で扱い、共通 UI の見た目は揃える。

## 7. 公開トップ `/`

### 7.1 役割
- サービス概要と公開可能な運用状況を短時間で理解させる。
- ログイン導線は提供するが、主役にはしない。

### 7.2 API 項目と表示対応
| API 項目 | 画面表示名 | 表示ルール |
|---|---|---|
| `operating_days` | 当月稼働日数 | `xx日` 形式で表示する |
| `batch_runs_total` | 総実行回数（累計） | 3桁区切りで表示する |
| `success_rate` | 当月成功率 | `%` を付けて表示する |
| `avg_duration_sec` | 当月平均処理時間 | `xx.x 秒` 形式で表示する |
| `updated_at` | 最終更新日時 | JST で表示する |

### 7.3 情報構造
1. ヘッダ
2. ヒーロー
3. 匿名集計サマリ
4. 公開範囲の説明

| セクション | 主な役割 | 主な内容 |
|---|---|---|
| ヘッダ | ブランド識別と最小導線 | 横長ロゴ画像、ログインボタン |
| ヒーロー | サービス概要の提示 | 見出し、説明文、最終更新日時 |
| 匿名集計サマリ | 実績の要約表示 | 4つの匿名集計カード |
| 公開範囲の説明 | 公開内容の制約説明 | 匿名集計のみであることの説明 |

### 7.4 レイアウト
- デスクトップは `暗色ヘッダ -> 暗色ヒーロー -> 明色サマリ -> 中間面の説明` の縦構成とする。
- ヒーローは 1 カラムで構成し、ボタンを置かない。
- 匿名集計カードはデスクトップで `2 x 2`、モバイルで 1 カラムとする。
- 公開トップのヘッダ導線は共通ヘッダの右側アクションとして `ログイン` のみを置き、GitHub 等の外部導線は置かない。

### 7.7 見た目のルール
- 見出しは `売買判断を、感覚ではなく戦略で。` を固定で用いる。
- 公開範囲の説明はカード化せず、本文と中間面で見せる。
- 数値の単位は必ず UI 側で明示する。

### 7.8 状態表示
- ローディングは匿名集計カード部分のみスケルトン化する。
- エラー時は匿名集計セクション直前に簡潔なエラー文言と `再試行` を置く。
- 項目単位の欠損は `--` を基本とする。

### 7.9 モバイル方針
- すべて 1 カラムで積み上げる。
- 暗色ヒーローの高さを伸ばしすぎず、ファーストビューで主要情報が見えるようにする。
- ログイン導線はヘッダ右上の 1 箇所に固定する。

## 8. 公開導線 `/login`

### 8.1 役割
- OIDC ログイン開始前の短い遷移ページとして扱う。
- 主な役割は `ログイン開始の説明` `再試行導線` `公開トップへの退避導線` の 3 点に限定する。

### 8.2 情報構造
1. 認証開始カード

| ブロック | 主な役割 | 主な内容 |
|---|---|---|
| 認証開始カード | ログイン遷移の主説明と主操作 | 見出し、短い説明、状態表示、主ボタン、戻る導線 |

### 8.3 レイアウト
- デスクトップ、モバイルともに中央寄せの 1 カラムを基本とする。
- ページの主役は 1 枚の白カードに限定する。
- ヘッダは全ページ共通ヘッダを使い、右側アクションだけを `公開トップへ戻る` に切り替える。

### 8.4 見た目のルール
- 見出しは 2 行以内、本文は 3 行以内を基準にする。
- 開発用の設定値一覧や診断情報を本番 UI に含めない。
- 主アクションは 1 つだけを強く見せる。

### 8.5 状態表示
- 初回表示時は `認証プロバイダへ移動します` などの進行文言を置く。
- リダイレクト失敗時はカード内にエラーを差し込み、主ボタンを `再試行` に切り替える。
- 開発用の補助情報が必要な場合は、別文書または開発専用 UI へ分離する。

### 8.6 モバイル方針
- カードは 1 枚に絞り、説明文とボタンの順で素直に積む。
- ボタン群は縦積みまたは折り返しを許容する。

## 9. 公開導線 `/logout`

### 9.1 役割
- ログアウト開始前の短い遷移ページとして扱う。
- ログイン不要で開けるが、機密情報は表示しない。

### 9.2 情報構造
1. ログアウト案内カード

| ブロック | 主な役割 | 主な内容 |
|---|---|---|
| ログアウト案内カード | 遷移前の案内と主操作 | 見出し、短い説明、ログアウト継続、公開トップへの戻り導線 |

### 9.3 レイアウト
- `/login` と同じ 1 カラムの遷移ページとする。
- 独自の新規ビジュアルは作らず、共通の遷移ページレイアウトを流用する。
- ヘッダは全ページ共通ヘッダを使い、右側アクションだけを `公開トップへ戻る` に切り替える。

### 9.4 状態表示
- ログアウトエンドポイント接続前は、暫定状態であることだけを簡潔に示す。
- エラー時はカード内で扱い、ページ全体を差し替えない。

## 10. 認証後サマリ `/app`

### 10.1 役割
- システム横断の現況を最短で把握するページとする。
- `全体の更新有無` `状態件数の偏り` `各システム詳細への遷移` を一画面で成立させる。

### 10.2 API 項目と表示対応
| API 項目 | 画面表示名 | 表示ルール |
|---|---|---|
| `system_count` | システム数 | 単独メトリクスとして表示する |
| `latest_run_at` | 全体の最終実行 | JST で表示する。`null` は `未実行` |
| `status_counts.succeeded` | 成功 | 件数カードまたは要約行で表示する |
| `status_counts.failed` | 要確認 | 件数カードまたは要約行で表示する |
| `status_counts.not_run` | 未実行 | 件数カードまたは要約行で表示する |
| `systems[]` | システム一覧 | API 返却順で表示する |

### 10.3 情報構造
1. `PageHeader`
2. `AppSectionNav`
3. 横断サマリメトリクス
4. システム一覧

### 10.4 レイアウト
- デスクトップは `ページヘッダ + アプリ内セクションナビ -> 要約カード -> システム一覧` の縦構成とする。
- システム一覧は主役なので、過度にサイド情報へ分割しない。
- 一覧はデスクトップでは行、モバイルではカードへ切り替える。
- ヘッダはトップページと同じ共通ヘッダを使い、右側アクションは `Logout` のみとする。
- `Watchlist` への導線は `PageHeader` 直下の `AppSectionNav` に置く。
- `/app` は `Summary` そのものなので、`AppSectionNav` では `Summary` を選択中ラベルとして見せ、ボタン化しない。

### 10.7 見た目のルール
- `system_code` を先頭、`system_name` を主見出しとして扱う。
- `failed` は危険色で塗りつぶさず、件数とラベルで注意喚起する。
- `AppSectionNav` はページ見出しの補助導線として扱い、主 CTA の強さにはしない。
- `PageHeader` に要約カードと同じメトリクスを重ねて置かず、`全体の最終実行` は要約カード側へ集約する。
- 詳細導線は行末のリンクまたは小ボタンとし、行全体を主ボタン化しない。

### 10.8 状態表示
- ローディング時はメトリクス 5 項目と一覧行 3 件程度のスケルトンを出す。
- エラー時は一覧パネル内にエラー表示と `再試行` を置く。
- `systems[] = []` は `システムがまだ登録されていません` の空状態で扱う。

### 10.9 モバイル方針
- メトリクスは 2 列または 1 列に落とす。
- システムカードは `状態 -> システム名 -> system_code -> 最新実行` の順で積む。

## 11. システム別最新結果 `/app/systems/:system_code`

### 11.1 役割
- `signals[]` を主役にし、特に `BUY` 判定を最短で視認できることを優先する。
- run 履歴ページは持たないため、最新 1 回分の文脈をページ先頭で補う。

### 11.2 API 項目と表示対応
| API 項目 | 画面表示名 | 表示ルール |
|---|---|---|
| `system_code` | システムコード | ページヘッダの補助情報として表示する |
| `system_name` | システム名 | ページ主見出しとして表示する |
| `latest_run_id` | 最新実行 ID | 詳細メタ情報として表示する |
| `latest_run_at` | 最新実行日時 | JST で表示する。`null` は `未実行` |
| `updated_at` | 更新日時 | 補助メタとして表示する |
| `signals[].priority_rank` | 優先度 | API 返却順を維持して表示する |
| `signals[].ticker` | 銘柄コード | 補助見出しとして表示する |
| `signals[].name` | 銘柄名 | 主見出しとして表示する |
| `signals[].decision` | 判定結果 | 最も強い視覚要素として pill で表示する |
| `signals[].reason` | 判定理由 | 初期版では補助テキスト、非表示でもよい |

### 11.3 情報構造
1. `PageHeader`
2. `AppSectionNav`
3. 実行メタ情報
4. シグナル一覧

### 11.4 レイアウト
- 上部は `system_name + system_code + 最新実行日時` をまとめたヘッダパネルとする。
- `PageHeader` 直下に `AppSectionNav` を置き、`Summary` `Watchlist` への退避導線を共通位置に保つ。
- その下に実行メタの小パネルを置き、さらにシグナルカードを並べる。
- シグナルカードは `1 列 -> 2 列 -> 3 列` を基本とする。

### 11.7 見た目のルール
- `BUY` は pill とカード内アクセントで強調する。
- `NO_SIGNAL` は失敗ではなく「対象なし」なので、弱い表現で扱う。
- 将来の追加ステータスも、色ではなくラベルで読めるようにする。

### 11.8 状態表示
- `latest_run_at = null` かつ `signals = []` は `まだ最新判定はありません` の空状態とする。
- `latest_run_at` があり `signals = []` は `今回の判定対象はありませんでした` とする。
- `404` は `不明なシステムです` のページ内エラーとして扱い、`/app` へ戻る導線を出す。

### 11.9 モバイル方針
- メタ情報は横並びに固執せず折り返す。
- シグナルカードは必ず 1 列で積み、優先度順を縦に読めることを優先する。

## 12. watchlist `/app/watchlist`

### 12.1 役割
- 絞り込み条件を操作しながら対象銘柄を探す画面とする。
- 入力フォームより結果一覧を主役にする。

### 12.2 API 項目と表示対応
| API 項目 | 画面表示名 | 表示ルール |
|---|---|---|
| `q_ticker` | Ticker | 完全一致検索。短い例示だけを置く |
| `system_code` | System Code | 完全一致フィルタ |
| `category_code` | Category Code | 完全一致フィルタ |
| `is_active` | Active | 初期値は `true` を選択状態で見せる |
| `items[].ticker` | Ticker | 一覧の主見出し |
| `items[].category_code` | Category | 補助ラベルまたは列として表示する |
| `items[].systems[]` | Systems | コード pill 群で表示する |
| `items[].latest_decisions_by_system` | Latest Decisions | 判定 pill 群で表示する |
| `items[].is_active` | Active 状態 | status pill で表示する |
| `items[].updated_at` | 更新日時 | JST で表示する |
| `next_cursor` | 追加取得導線 | `null` でない場合のみ `さらに読み込む` を表示する |

### 12.3 情報構造
1. `PageHeader`
2. `AppSectionNav`
3. フィルタパネル
4. 結果一覧
5. 追加取得導線

### 12.4 レイアウト
- ヘッダはトップページと同じ共通ヘッダを使い、右側アクションは `Logout` のみとする。
- `PageHeader` 直下に `AppSectionNav` を置き、`Watchlist` を現在地ラベル、`Summary` を戻り導線として扱う。
- フィルタパネルは結果一覧の上に置き、左カラムだけへ寄せない。
- デスクトップでは 4 項目を 1〜2 行で整理する。
- 結果一覧はモバイルではカード、広い画面では表形式を基本とする。
- 横スクロール常態化は避ける。

### 12.7 見た目のルール
- `Ticker` を最も強いテキストとする。
- `Systems` はコード pill、`Latest Decisions` は判定 pill の並びで見せる。
- `updated_at_desc` 固定であることは補助テキストで伝え、ソート UI は初期実装で持たない。

### 12.8 状態表示
- ローディング時はフィルタパネルを残し、結果一覧だけスケルトンにする。
- `items = []` は `条件に一致する銘柄はありません` の空状態で扱う。
- 入力エラーは入力欄直下で短く示す。
- `next_cursor != null` の場合のみ一覧下部に `さらに読み込む` を出す。

### 12.9 モバイル方針
- フィルタは 1 カラムで積み、`is_active` を最後に置く。
- 結果カードは `Ticker -> 状態 -> Category -> Systems -> Latest Decisions -> updated_at` の順で積む。
