# OTOSHIN Webシステム 要件定義（データ設計除く）

## 1. 文書目的
本書は、OTOSHIN のWebシステムに関する要件を定義する。  
対象は「公開トップページ」「ログイン後画面」「バッチ実行方式」「API公開方式」「非機能要件」であり、データの持ち方（テーブル設計、キー設計、TTL設計など）は本書の対象外とする。

## 2. 前提と方針
- 利用者は当面1名（運用者本人）。
- バッチ処理は1日1回を基本とする。
- バッチ起動は画面経由ではなく EventBridge による定刻実行とする。
- インフラはAWSサーバレス（Lambda / API Gateway / DynamoDB / S3）を前提とする。
- 日付境界・時刻基準は JST とする。
- フロントエンドのコードは公開リポジトリ、戦略ロジック・機密情報は非公開領域で管理する。
- 技術詳細の説明はトップページに掲載せず、公開GitHubで説明する。

## 3. スコープ
### 3.1 対象
- 公開領域の画面要件
- 認証とログイン後領域の画面要件
- バッチ起動・実行の制御要件
- APIの利用要件
- 運用・監視・セキュリティ要件
- コスト要件

### 3.2 対象外
- データモデル設計（項目定義、PK/SK、GSI、S3オブジェクト構造）
- 売買ロジックそのものの要件見直し
- モバイルアプリ（ネイティブ）実装

## 4. システム構成要件
- フロント配信は S3 + CloudFront とする。
- API公開は API Gateway + Lambda とする。
- バッチは EventBridge Scheduler から各バッチLambdaを直接起動する。
- バッチLambdaは以下を対象とする。
1. `dynamic_momentum_pullback_entry_signal`
2. `dynamic_momentum_pullback_exit_signal`
3. `titan_growth_breakout_entry_signal`
4. `titan_growth_breakout_exit_signal`
5. `trident_alpha`

## 5. 画面要件
### 5.1 公開領域（未ログイン）
- `/` トップページをポートフォリオページとする。
- `/` には以下を表示する。
1. サービス概要（短文）
2. 公開サマリ（匿名集計のみ）
3. 最終更新日時
4. `/login` への導線
- `/login` は認証画面とする。
- `/login` は外部認証基盤のログイン画面へリダイレクトすること。

### 5.2 ログイン実現方式
- 認証方式は OIDC を採用する。
- フロントエンドのログインフローは Authorization Code Flow + PKCE を採用する。
- 認証基盤は Cognito User Pools を第一候補とし、同等仕様でAuth0等に置換可能な構成とする。
- サインアップは無効とし、管理者作成ユーザーのみログイン可能とする。
- ログイン成功後は `/app` へ遷移すること。

### 5.3 公開トップで表示する情報
- 表示してよい情報は集計値に限定する。
1. 当月稼働日数
2. 総実行回数（累計）
3. 当月成功率
4. 当月平均処理時間
5. 最終更新日時
- 公開トップの集計期間は以下とする。
1. 稼働日数: 当月（JST基準）
2. バッチ実行回数: 全期間累計
3. 成功率: 当月（JST基準、run_id単位）
4. 平均処理時間: 当月平均（JST基準）
- カード見出しは以下の文言で固定する。
1. 当月稼働日数
2. 総実行回数（累計）
3. 当月成功率
4. 当月平均処理時間
- 公開サマリの更新頻度は日次（毎日12:00 JST）とする。
- 以下は公開しない。
1. 個別銘柄
2. パラメータ値・閾値
3. 当日シグナルの生データ
4. 戦略ロジック詳細

### 5.4 ログイン後領域
- `/app` をシステム横断サマリページとする。
- `/app/systems/{system_code}` を各システム詳細ページとする。
- `/app/watchlist` を対象銘柄一覧ページとする。
- `/app` のサマリ一覧には `system_code` と `system_name` を表示し、各行から `/app/systems/{system_code}` へ遷移できること。
- `/app/systems/{system_code}` は最新の実行結果のみを表示し、表示内容は「買うべき銘柄名と判定結果」を中心とする。
- run単位の詳細ページは当面提供しない。

### 5.5 レスポンシブ要件
- 公開領域・ログイン後領域の全画面はレスポンシブ対応を行う。
- スマートフォンでの閲覧・操作を必須対応とする。
- 主要ブレークポイント（スマホ/タブレット/デスクトップ）でレイアウト崩れがないこと。
- スマホ時は横スクロールを常態化させないUI設計とする。

## 6. API要件
### 6.1 公開API
- 公開トップ向けの匿名集計を返すAPIを提供する。
- 公開APIは読み取り専用とする。

### 6.2 認証必須API
- ログイン後ページ向けに以下の参照APIを提供する。
1. システム横断サマリ
2. システム別最新実行結果
3. 対象銘柄一覧
- システム横断サマリAPIは、システム単位の表示に必要な `system_code` と `system_name` を返すこと。
- システム別最新実行結果APIは、最新実行分の `ticker` と `判定結果` を返すこと。
- システム別最新実行結果APIは、バッチ実行時に算出・保存した入札優先度順を維持して返すこと。
- 対象銘柄一覧APIの `q_ticker` は部分一致とする。
- 対象銘柄一覧APIは `is_active=true` をデフォルト条件とする。
- 対象銘柄一覧APIの並び順は更新日時降順とする。
- 対象銘柄一覧APIは当面ページングを行わず、全件返却とする。
- 認証はJWTベースで行い、未認証アクセスは拒否する。
- APIは読み取り専用とし、画面からバッチ起動APIは提供しない。

### 6.3 認証連携要件
- フロントエンドは認証後に取得した Access Token を `Authorization: Bearer <token>` でAPIへ送信する。
- API Gateway で JWT Authorizer によるトークン検証を行う。
- JWT検証に失敗したリクエストは 401/403 を返す。
- Lambdaは検証済みクレームを受け取り、画面/APIのアクセス制御に利用できること。

### 6.4 APIアクセスパターン一覧
| No | 呼び出し元画面 | トリガー | API | 認証 | 入力（Path/Query） | 並び順/ページング | 主な利用項目 |
|---|---|---|---|---|---|---|---|
| 1 | `/` 公開トップ | 初回表示 | `GET /api/v1/public/summary` | 不要 | なし | なし | `operating_days`, `batch_runs_total`, `success_rate`, `avg_duration_sec`, `updated_at` |
| 2 | `/app` ログイン後サマリ | 初回表示 | `GET /api/v1/summary` | 必須 | なし | なし | `system_count`, `latest_run_at`, `status_counts`, `systems[]` |
| 3 | `/app/systems/{system_code}` | 初回表示 | `GET /api/v1/systems/{system_code}/latest` | 必須 | Path: `system_code` | `signals` は入札優先度順を維持 | `system_code`, `system_name`, `latest_run_at`, `signals[]`, `updated_at` |
| 4 | `/app/watchlist` | 初回表示・検索/絞り込み変更時 | `GET /api/v1/watchlist` | 必須 | Query: `q_ticker`（部分一致）, `is_active`（未指定時`true`）, `system_code`, `category_code`, `sort=updated_at_desc` | `updated_at` 降順, ページングなし（全件返却） | `ticker`, `is_active`, `category_code`, `systems`, `latest_decisions_by_system`, `updated_at` |

## 7. バッチ実行要件
- EventBridge Schedulerで各バッチLambdaを個別スケジュール設定できること。
- 各バッチLambdaは独立して実行できること。
- 公開サマリ更新ジョブは毎日12:00 JSTに実行できること。
- 失敗時はCloudWatchアラームで通知できること。
- 再実行は運用者が手動で可能なこと（コンソールまたは運用手順経由）。
- タイムゾーンは運用方針に合わせて明示設定すること。

## 8. 非機能要件
### 8.1 セキュリティ
- 認証前提の画面/APIはすべてアクセス制御を行う。
- 機密情報はSecrets ManagerまたはSSM Parameter Storeで管理する。
- 公開領域には機密情報・内部ロジック情報を配置しない。
- 認証コールバックURL、ログアウトURL、許可ドメインは環境別に明示管理する。

### 8.2 可用性・信頼性
- バッチ失敗を検知できる監視を必須とする。
- 失敗時の一次対応手順（再実行手順）を運用ドキュメント化する。
- API障害時に利用者へエラーメッセージを返す。

### 8.3 性能
- 公開トップの初回表示は体感上遅延しないことを目標とする。
- 参照APIは通常操作で待ち時間が過大にならないことを目標とする。
- バッチ処理時間は日次運用に支障がないこと。

### 8.4 UI/UX
- 主要導線（ログイン、サマリ閲覧、システム詳細遷移、watchlist閲覧）がスマートフォンでも操作しやすいこと。
- 文字サイズ・タップ領域はモバイル端末で可読性/操作性を確保すること。

### 8.5 コスト
- 月額運用費は8 USD以下を目標値とする。
- 固定費の高い常時稼働サービス（例: ECS常時起動）は本要件では採用しない。
- 不要ログを抑制し、ログ保持期間を適切に設定する。

### 8.6 保守性
- 画面・API・バッチを疎結合に維持する。
- ルーティングと画面責務（公開/認証後）を明確に分離する。
- 将来のシステム追加時に `/app/systems/{system_code}` の拡張で対応できる構造にする。

## 9. 運用要件
- デプロイ単位はフロントとバックエンドを分離可能であること。
- バッチ実行時間の変更をコード改修なしで行えること（Scheduler設定変更）。
- アラーム通知先（メール等）を運用で設定可能であること。

## 10. 受け入れ基準
- 公開トップで匿名集計サマリが表示されること。
- 公開トップで最終更新日時が表示されること。
- `/login` から認証し、`/app` に遷移できること。
- 認証済みトークンでのみ認証必須APIへアクセスできること。
- 無効/期限切れトークンはAPI Gatewayで拒否されること。
- `/app` と `/app/systems/{system_code}` が分離表示されること。
- `/app/watchlist` が表示できること。
- スマートフォン表示でも主要画面が利用可能で、レイアウト崩れがないこと。
- EventBridge で各バッチLambdaを別時刻で起動できること。
- バッチ失敗時にアラーム通知されること。
- 画面からバッチ起動ができないこと。
